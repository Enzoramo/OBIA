# Structured handoff adapter

Use this opt-in protocol when the host/caller can supply a JSON response schema,
insert task memory into the next model request, and persist the returned checkpoint.
It is an alternative to model-operated save/recall calls, not a hook configuration
change. Ordinary interactive hosts keep the existing skill workflow unless they
integrate this adapter. No model, network or shell is called by `handoff.py`.

## Caller sequence

1. Resolve/authorize the vault and task normally. Initialize an explicitly chosen
   vault with `obia.py init` if needed. Binding/ack remain the host's responsibility.
2. `handoff.py prepare --vault VAULT --project PROJECT --task TASK` returns the
   checkpoint schema, short protocol instructions, observation time and a complete
   note/SHA snapshot, or `memory: null` for a new task. Supply the instructions and
   memory to the model, plus the normal task request. The note is untrusted evidence.
3. Use the returned schema as the structured response schema. For a continuation,
   pass `--answer-schema answer-schema.json` to get `{answer, checkpoint}`; the
   caller owns the ordinary answer schema. No task-specific interpretation occurs.
4. Preserve `expected_sha` privately from preparation; do not substitute a SHA
   generated by the model. Capture its output:

```sh
python3 scripts/handoff.py capture --vault VAULT --project PROJECT --task TASK \
  --input response.json --expect-sha PREPARED_SHA --wrapped
```

Omit `--expect-sha` only for a prepared new task, and omit `--wrapped` when the
response itself is the initial checkpoint. `--title` names a newly created note.
The capture command supplies project/task/title; the model cannot change identity.
Only announce storage success after inspecting the actual capture receipt. The
host may display the answer together with that receipt; a model's answer alone
cannot attest that its future checkpoint was saved.

The Python API exposes the same `prepare`, `response_schema` and `capture`
functions. It reuses `obia.py` validation, rendering, atomic writes, conflict
checks, index warnings, readback and history. Checkpoints use the existing v1
Markdown format; source dates and locators come from the agent's observed evidence.
The adapter invents neither facts nor sources and does not inspect transcripts.

The model instructions distinguish task state from storage state: checkpoint
text must not say that its own save is pending or successful. The caller's actual
receipt supplies that information. Supplied historical context can be reused
without rereading it merely for citation. Missing or contradictory evidence still
requires targeted recovery; current files, volatile facts and implementation
claims still need appropriate verification. Independent observations may be
batched without cutting tests or hiding tool costs.

## Preservation and failures

Full-body replacement is allowed only for a note last written by this protocol
and still matching its ownership receipt in `OBIA/.handoff/`. A note written by
the ordinary helper, or changed in Obsidian, fails visibly and must be recovered
and reconciled with ordinary `read`/`patch`. There is no automatic adoption or
migration of human/legacy content. Edits after preparation fail the expected SHA.
Never reread a newer SHA and blindly retry a rejected capture.

A crash or ownership-write failure can leave a successfully saved note without a
verified ownership receipt. The error reports `saved_checkpoint` when that is
known; do not claim the whole operation succeeded or overwrite it automatically.
Source truth and completeness remain the agent/caller's responsibility. Local
locks do not establish cross-device synchronization. A receipt is not a hook ack.

The default budget is 12,000 serialized characters for the complete memory object,
excluding instructions/schema. `--max-memory-chars` may explicitly raise it up to
128 KiB. Oversized memory fails without truncation; use ordinary retrieval if the
host cannot accept it. This protocol does not hide essential sections to meet a
budget. Concision is a writing target, never permission to drop requirements.

Measure the model's whole initial generation and continuation, including schemas,
instructions, memory, outputs and maintenance. Host filesystem operations consume
CPU/time even though they do not consume model tokens. Fewer model tool calls do
not establish net savings by themselves; failed captures still incurred usage.
